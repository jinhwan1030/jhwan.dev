## 시작은 출품작이었다

산길안심은 산악기상 기반 AI 산행안전 예보 서비스로 시작했다. 산에 가기 전 "오늘 이 산을 가도 괜찮은가"를 안전, 주의, 위험으로 빠르게 판단하게 해주는 서비스가 목표였다.

처음에는 제1회 산림과학 AI 활용 경진대회 출품을 염두에 두고 만들었다. 그런데 결국 기획서를 제출하지 못했다. 그래서 이 프로젝트는 완성된 출품작도, 공개 운영 중인 서비스도 아닌 애매한 상태로 남았다.

그렇다고 버릴 프로젝트는 아니었다. 코드를 다시 보니 FastAPI API, 위험지수 엔진, 검수된 브리핑 샘플, 위험지도, 테스트까지 생각보다 많은 것이 남아 있었다. 문제는 완성도가 아니라 맥락이었다. 이 글은 그 맥락을 다시 붙이는 회고다.

## 무엇을 만들었나

산길안심은 산행 위험도를 0~100점으로 계산하고, 결과를 한국어 브리핑으로 보여주는 프로토타입이다.

- 산악 관측지점 기반 위험도 조회
- MRI(Mountain Risk Index) 0~100점 계산
- `안전`, `주의`, `위험` 등급 분류
- 저체온, 강풍, 강수시정, 산불, 산사태 세부 점수
- 위험 요인을 한국어 브리핑으로 요약
- 10개 대표 산악 관측지점 위험지도
- 6개 시연용 샘플 케이스
- 데이터 출처와 한계 페이지
- FastAPI 백엔드와 정적 PWA 프론트엔드
- pytest 기반 API, 위험지수, 브리핑 테스트

## 기술 스택

```text
Frontend: Static HTML/CSS/JS, PWA
Map: Leaflet
Backend: FastAPI
Risk Engine: Rule-based MRI
Tests: pytest, httpx ASGITransport
Infra: Docker, Docker Compose, Nginx
Deploy Target: GHCR + Watchtower
```

BabyWeather에서 운영하며 익숙해진 구조를 일부 재사용했다. FastAPI로 API를 만들고, 정적 프론트엔드를 Nginx로 서빙하고, Docker 이미지로 배포하는 방식이다. 다만 산길안심은 운영 서비스라기보다 발표와 검증을 위한 프로토타입에 더 가깝다.

## MRI: 산행 위험을 하나의 점수로 접기

핵심은 MRI(Mountain Risk Index)다. 산행 위험을 다섯 가지 축으로 나누고, 각 점수를 더해 100점 만점으로 만든다.

| 항목 | 최대 | 주요 기준 |
|------|------|-----------|
| 저체온 | 18 | 체감온도와 고도 |
| 강풍 | 16 | 산지 풍속 기준 |
| 강수시정 | 16 | 1시간 강수량, 강수형태, 시정 |
| 산불 | 25 | 산불위험 등급 |
| 산사태 | 25 | 3시간/12시간 누적강수와 선행강우 |

등급은 단순하게 나눴다.

| 점수 | 등급 |
|------|------|
| 0~20 | 안전 |
| 21~40 | 주의 |
| 41~100 | 위험 |

이 구조의 장점은 설명 가능성이다. LLM이 위험도를 "생성"하는 것이 아니라, 규칙 기반 엔진이 먼저 점수와 위험 요인을 만든다. 브리핑은 그 결과를 사람이 읽기 좋게 바꾸는 역할에 가깝다.

## 브리핑은 LLM보다 검수 텍스트를 먼저 썼다

처음부터 LLM 호출을 전제로 만들면 데모가 흔들릴 수 있다. API 키, 비용, 응답 지연, hallucination 문제가 모두 들어오기 때문이다.

그래서 브리핑 모듈은 네 단계 폴백으로 만들었다.

1. `case_id`가 있으면 검수된 샘플 브리핑 사용
2. 등급과 위험 요인이 비슷한 샘플을 찾아 사용
3. LLM API 키가 있으면 LLM 호출
4. 그래도 없으면 등급별 기본 문구 사용

현재는 LLM 호출이 비활성화되어 있다. 대신 `data/briefing_samples.json`에 검수된 데모 브리핑을 넣어두었다. 발표나 시연에서는 이 편이 오히려 안정적이다.

## 데모 케이스

외부 API가 없어도 서비스 흐름을 보여줄 수 있도록 6개 케이스를 만들었다.

| case_id | 산 | 주요 위험 | 등급 |
|---------|----|-----------|------|
| `jirisan_landslide` | 지리산 천왕봉 | 누적강수와 산사태 | 위험 |
| `seoraksan_wind` | 설악산 대청봉 | 강풍과 산불 | 위험 |
| `hallasan_cold` | 한라산 백록담 | 저체온과 강풍 | 주의 |
| `bukhansan_fire` | 북한산 백운대 | 산불위험과 저습도 | 주의 |
| `songnisan_rain` | 속리산 천왕봉 | 강수와 시정불량 | 주의 |
| `gyeryongsan_safe` | 계룡산 삼불봉 | 쾌적한 산행 조건 | 안전 |

데모 모드에서는 외부 API 없이 이 샘플 데이터만으로 API와 화면이 동작한다. 이건 대회 발표를 염두에 둔 선택이었다. 네트워크나 API 키 문제 때문에 시연이 깨지는 상황을 피하고 싶었다.

## 구현한 화면

프론트엔드는 두 가지 흐름을 갖는다.

첫 화면에서는 산을 선택하고 위험도를 조회한다. 결과는 등급, 점수, 세부 점수, 위험 요인, 안전 브리핑으로 구성된다.

두 번째 화면은 위험지도다. Leaflet 지도를 사용해 10개 대표 관측지점의 점수와 등급을 마커로 표시한다. 지도에서 지점을 누르면 상세 조회로 이동할 수 있다.

정적 HTML/CSS/JS로 만들었고, PWA manifest도 붙였다. 복잡한 프레임워크 없이 빠르게 발표 가능한 화면을 만드는 쪽을 택했다.

## 테스트와 검증

이 프로젝트에서 잘한 부분은 테스트를 꽤 일찍 넣은 것이다.

- API 라우터 통합 테스트
- MRI 점수 계산 테스트
- 브리핑 생성 테스트
- 안전 파싱 테스트
- `scripts/validate_mri.py` 검증 스크립트

특히 MRI는 임계값 하나가 바뀌면 등급이 흔들리기 때문에, 데모 케이스와 경계값 케이스를 함께 검증하도록 했다.

```bash
venv/bin/python -m pytest tests/ -v
venv/bin/python scripts/validate_mri.py
```

## 어디서 멈췄나

멈춘 지점은 코드가 아니라 제출물이었다. 서비스 형태는 어느 정도 만들었지만, 경진대회에 필요한 기획서와 문제정의 문서를 제때 완성하지 못했다.

출품작이라면 다음 질문에 명확히 답해야 했다.

- 기존 산악기상 서비스와 무엇이 다른가?
- AI 활용 지점은 어디인가?
- 위험지수 임계값은 어떤 근거로 정했는가?
- 사용자는 누구이고, 어떤 상황에서 이 서비스를 쓰는가?
- 실제 산행 안전에 어떤 방식으로 도움이 되는가?

코드는 이 질문들에 대한 재료를 갖고 있었지만, 답변으로 정리되어 있지는 않았다. 그래서 프로젝트가 어중간해 보였다.

## 그래도 남은 것

이 프로젝트는 실패작이라기보다, 문서화되지 못한 프로토타입에 가깝다.

남은 자산은 분명하다.

- 산악기상 위험을 하나의 점수로 접는 규칙 기반 엔진
- LLM 호출 전 검수 텍스트를 우선하는 브리핑 구조
- 외부 API 실패에 대비한 데모 모드
- 위험지도와 상세 조회를 나눈 화면 구성
- 테스트 가능한 위험지수 임계값 구조

특히 "LLM이 판단하지 않고, 규칙 기반 결과를 설명하게 한다"는 방향은 계속 가져갈 만하다. 안전 서비스에서는 그 편이 더 설명 가능하고, 운영자가 고칠 수 있다.

## 다음에 다시 한다면

다시 손댄다면 코드보다 기획서를 먼저 쓸 것이다.

1. 사용자 상황을 먼저 좁힌다. 예: 초보 등산객, 국립공원 방문객, 산악회 운영자.
2. 위험지수 기준을 출처별로 문서화한다.
3. 실시간 API 연결 범위를 작게 잡는다.
4. LLM은 판단자가 아니라 브리핑 편집자로 둔다.
5. 지도보다 "오늘 이 산을 가도 되는가"를 더 앞에 둔다.

그리고 출품용 프로젝트라면 마감 전날 코드를 더 만드는 것보다, 심사자가 읽을 문제정의와 평가 흐름을 먼저 완성해야 한다.

## 마치며

산길안심은 공개 운영 서비스가 되지는 못했다. 기획서도 제출하지 못했다. 하지만 이 프로젝트 덕분에 안전 도메인에서 중요한 것은 멋진 AI 문구보다 설명 가능한 기준, 데이터 출처, 실패해도 깨지지 않는 흐름이라는 걸 다시 배웠다.

그래서 이 프로젝트는 "못 낸 출품작"으로만 남기기엔 아깝다. 다음에는 README와 회고부터 붙이고, 필요하면 더 작고 선명한 형태로 다시 살려볼 수 있을 것 같다.
